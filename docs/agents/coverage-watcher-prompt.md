# カバレッジウォッチャー エージェントプロンプト（テンプレート）

`{connector}` を実際のコネクタ名（ディレクトリ名。例: `lstep`）に置き換えて使う、
1コネクタを深掘りするためのエージェントプロンプトのテンプレート。

このテンプレートは lstep コネクタで手動検証した動きを再現するためのもの。
lstep の深掘りでは、公式ドキュメント（docs.lineml.jp）を精査した結果
`list_templates` / `upload_media` の2ツールを実装し、一方で候補に挙がっていた
`get_friend`（友だち単体取得）は **ドキュメント上に実在が確認できなかったため
実装を見送った**。この「作れそうでも、確認できないものは作らない」判断こそが
このワークフローの核であり、以下のプロンプトもそれを再現するように設計している。

---

## プロンプト本体

```
あなたは mcp-jp リポジトリのコネクタ「{connector}」のカバレッジ深掘りを担当する。

目的: 「{connector}」が実装しているツールと、公式APIが実際に提供している機能との
差分を確認し、証拠（公式ドキュメントの記載）に基づいて追加すべきツールがあれば
実装する。証拠が無いものは絶対に実装しない。

## 手順

1. 前提を読む。
   - `docs/strategy.md` — このリポジトリの品質基準（「載せたものは全部ちゃんと動く」
     を本数より優先する、書き込み系は監査・確認前提で慎重に扱う、等）。
   - `{connector}/src/{connector}_mcp/server.py` — 現在実装済みのツール一覧・
     エンドポイントの叩き方。
   - `{connector}/README.md` — ツール一覧、既知の制約セクション（すでに
     「実在が確認できず見送った」機能が書かれていないか）。
   - `notes/coverage_state.json` の `connectors.{connector}` — 前回までの
     `tools` / `docs_url` / `last_deep_check` / `notes`。

2. 公式ドキュメントを取得する。
   - README に書かれた `docs_url`（無ければ自分で公式サイトの開発者ドキュメントを
     探す）を実際に開き、**今日時点で何が文書化されているか**を確認する。
   - ドキュメントが古い・移転している・404 になっている場合は、その旨を記録する
     （公式ドキュメント自体が信頼できない状態は、それ自体が重要な発見）。

3. 差分を洗い出す。
   - 実装済みツール一覧（server.py）と、ドキュメントに載っているエンドポイントを
     突き合わせ、「ドキュメントにはあるが未実装」の候補をリストアップする。
   - 各候補について、ドキュメント上で以下が明確に確認できるかをチェックする:
     - エンドポイントの実在（メソッド + パス）
     - リクエストパラメータ・レスポンスの形（何を渡し、何が返るか）
   - **確認できたものだけ**を「実装候補」とする。

4. 確認できなかったものは実装せず、理由を記録する。
   - これが最も重要なルール。「たぶんあるはず」「他社の類似APIにはある」
     「公式ブログには書いてあるが、汎用APIとしての固定仕様が見当たらない」
     といったケースは、**実装せず見送り、README の「既知の制約」に理由を書く**。
   - 判断に迷ったら lstep の `get_friend` ケースを思い出す: 「友だち単体取得」は
     一見あってもおかしくない機能だったが、`docs.lineml.jp` を精査した結果
     該当エンドポイントが存在せず、実装を見送った。これは失敗ではなく
     正しい判断であり、README にも「実在が確認できなかった」as-isで明記した。
     同様の状況になったら、遠慮なく「作らない」を選び、その根拠を書く。

5. 書き込み系（作成・更新・削除・送信・配信）のエンドポイントは特に慎重に扱う。
   - 実装する場合: ツールの description に、何が起きるか・取り消せるかどうか・
     対象範囲（1件か複数件か）を明示する。実データを書き換える／外部に送信する
     操作であることが AIエージェント側から見て明確に分かるようにする。
   - 実装を見送る場合: 「エンドポイントの実在が確認できないため」だけでなく、
     「実在するとしても読み取り中心の方針に照らしリスクが高いため」という
     理由も README に書いてよい（両方が理由になっているケースもある。
     lstep のメッセージ送信系がその例）。
   - 読み取り系より一段高いエビデンスのハードルを課すことを恐れない。

6. 実装したら、以下を必ず行う。
   - `{connector}/README.md` の「利用可能なツール」に追加したツールを記載する。
   - `{connector}/README.md` の「既知の制約」に、見送った機能とその理由を記載する
     （見送りが無ければこの手順は不要）。
   - `.venv/bin/pytest tests/test_structure.py tests/test_error_handling.py -v`
     を実行し、全て green であることを確認する（落ちたら直すまでコミットしない）。
   - 変更をローカルにコミットする。コミットメッセージは日本語、
     例: `feat: {connector}にlist_xxxを追加（公式ドキュメントで実在確認済み）`。
   - **リモートには push しない。PRも開かない。main に直接コミットしない**
     （現在のブランチ／ワークツリー上でのローカルコミットのみ）。

7. 最後に `notes/coverage_state.json` の `connectors.{connector}` を更新する。
   - `last_deep_check` を実行日（YYYY-MM-DD）に更新する。
   - `notes` に、今回追加したツール・見送った機能とその理由を簡潔に書く
     （次回の深掘りで同じ調査を繰り返さずに済むように）。
   - `tools` / `tool_count` / `docs_url` は `scripts/coverage_inventory.py` を
     再実行すれば自動更新されるので、手動で触らなくてよい
     （ただし触っても実行すれば上書きされるので実害はない）。

## 出力として期待するもの

- 確認済みの追加ツール（あれば）とその実装。
- 見送った機能とその理由（README「既知の制約」への追記）。
- 更新された `{connector}/README.md`。
- green なテスト結果。
- ローカルコミット1件（Japanese commit message）。
- 更新された `notes/coverage_state.json`（`last_deep_check` / `notes`）。
```
