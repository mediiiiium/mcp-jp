# コネクタ候補 選定マトリクス（叩き台）

新しいコネクタを「API があるから」で量産すると、(1) 公式 MCP に追い抜かれ、(2) 需要のない閲覧系を作り、(3) 鍵が取れず検証もできない、という消耗に陥る。
**着手前にこのマトリクスでスコアリングし、上位だけ作る。**

## スコアリング軸（各 0〜3 点、合計 12 点満点）

| 軸 | 0 点 | 3 点 |
|---|---|---|
| **A. 既存MCP不在の持続性** | 公式 MCP が既にある／半年内に出る兆候／**第三者の無料MCP・OSSラッパーが既にある** | 日本SMB特化・ベンダーがAIに消極的で当面来ない・**有志の実装も無い** |
| **B. 業務需要の強さ** | 単なる閲覧・ニッチ | 勤怠/請求/採用/在庫/CSなど日次業務でAI操作の価値が明確 |
| **C. API & 検証可能性** | API非公開／鍵が取れず疎通検証不能 | 安定したREST API公開＋開発者がテスト用鍵を取得可能 |
| **D. 日本SMB密着度** | グローバル大手（公式が必ず来る） | 国内SMBに広く普及し英語圏が作らない |

**判定:** 合計 **9 点以上を着手候補**、6〜8 は保留、5 以下は見送り。
A が 0（公式あり/直近GA/**第三者の無料実装あり**）なら**他が高くても見送り**（追い抜かれ確定のため）。

### A軸の訂正（2026-08-13）

当初 A は「**公式**MCP不在の持続性」だった。公式が来ないことだけを見ており、**第三者が無料で埋めている場合を見落とす**。

EDINET（金融庁の開示書類API）で実際に踏んだ。金融庁が MCP を出すことは当分ないので、旧定義では A は満点になる。
だが実際には既に2つ埋まっていた —— **EDINET DB**（REST 74エンドポイント・MCPサーバー・Web完全無料・API 100回/日まで無料・商用利用可）と、
**edinet-mcp**（PyPI / GitHub のOSS。XBRLパーサ＋MCPサーバー）。

> **原料が公開・無料・機械可読なほど、公式ではなく有志と無料サービスが先に埋める。**

「取りにくさ」を堀と読むと外す。見るべきは公式の不在ではなく**既存実装の不在**。

**適用範囲**: A軸は「**これから何に着手するか**」の選別基準であって、既に作ったものの評価軸ではない。
後から公式や第三者が出てくるのは織り込み済みで、実装そのものは MCP 開発の実績として残る。
`archive/` 送りは公開推奨先を公式へ切り替える整理であって、撤退ではない。
**日本SMB向け FDE を主戦場に置く方針はこれで動かさない。**

## 運用ルール

1. **着手前に必ず Web で裏取り**: ①**既存 MCP の有無 —— 公式**（ベンダー発表・`mcp.<service>.com`）**と第三者**（GitHub・**PyPI**・**npm**・MCPサーバー一覧サイト）**の両方を見る**②API ドキュメントの実在③テスト用クレデンシャル取得可否。
2. **既存MCP一覧の鮮度管理を自動化する**（README の表は手動だと必ず腐る）。月次で**公式・第三者の両方**の新規提供をチェックし（GitHub・PyPI・npm の検索を含む）、出たコネクタは `archive/` へ移す。→ `scripts/` に巡回スクリプトを置く想定。
   **実装済み34本にも遡って当てる** —— 追い抜かれているものが混じっている可能性がある。
3. **需要シグナルはコードでなく市場から引く**: 対象SaaSのコミュニティ/フォーラム/X で「ChatGPT/Claude で〇〇したい」の声、各社の API 利用事例。
4. 着手したら本表に行を追加し、スコアと裏取り日・出典を残す。

## 自動発掘との役割分担

`scripts/discover_candidates.py` が PRONI アイミツを月次でフルスキャンし、新規に Tier1
（即着手候補）入りしたサービスを洗い出す。本表とは役割が異なる:

- **自動（discover_candidates.py）**: 「候補が存在すること」を機械的シグナル（API硬判定・公式が出さない確度・利用者規模）で広く拾うところまで。
- **手動（本表）**: それを受けて、この A/B/C/D マトリクスで着手可否を最終判断する場所。自動側のシグナルは裏取りの出発点であり、A軸（公式MCP不在の持続性）などは必ず自動側の判定を鵜呑みにせず一次情報で確認する。

新規Tier1 が出たら、裏取り後にこの表へ行を追加する運用とする。

### なぜ GitHub Actions で回していないか

2026-06〜07 に月次スキャンと週次ウォッチを Actions に置いたが、**一度も成功しなかった**。
PRONI がデータセンターIPからの取得に中身のない `HTTP 202` を返す（ボット緩和）。
同じスクリプト・同じ User-Agent でも手元からは 744 件取れるので、差は送信元IPだけ。
self-hosted runner はこのリポジトリが public のため却下（fork PR が自宅マシンでコードを実行できる）。

加えて、スキャン結果には**着手前の候補サービス名**が含まれる。Actions 版は
それを public リポジトリの Issue として起票する作りだった（実害は出ていない。
WAF で手前で落ちていたため）。候補名は `mcp-private/` に留める設計と真正面から矛盾する。

現在は Mac 上の launchd で回している（`com.mediiiiium.discover.scan` 月次 /
`com.mediiiiium.discover.watch` 週次）。出力先は `mcp-private/` なので公開されない。
止まったらダッシュボードの候補ファネルに ⚠️ が出る。

## 既存実装との重複チェック（着手前に必ず）

- リポジトリ `/` 直下に同種コネクタが無いか（採用=herp/talentio、勤怠=kingtime/akashi/hrmos-kintai、請求=board/misoca/makeleaps/invox）。
- `archive/` に公式MCPで非推奨化したものが無いか。
